# Metacognition：研究思考軌跡紀錄

這個 skill 維護專案裡的 `research_log/` 目錄。它不只是實驗筆記，而是把**思考過程**本身記下來：想法從哪裡來、怎麼被證據改變、每個數字用什麼方法量的。

名稱來自心理學的「後設認知」（對自己思考的思考）。它要防範研究中最常見的幾種認知偏誤：

- **來源混淆（source monitoring error）**：把看到結果之後才想到的解釋，誤記成「一開始就是這樣設計的」。
- **後見之明偏誤（hindsight bias）**：知道結果後，回頭改寫當初的推理，好像「早就知道」。
- **協定混用**：把不同方法量出來、名稱相同的數字放在同一張表比較。

下面每條規則都是為了對付其中一種。理解原因比死守格式重要；遇到格式沒涵蓋的情況，依原則判斷。

## 目錄結構

```
research_log/
├── README.md                  使用說明，以及本專案的「因果線」定義
├── hypotheses.md              中樞索引：所有假設與狀態；最上方是「當前最前沿的待分析問題」
├── methods.md                 評估協定登記表：每種量測方法的定義、recipe、陷阱、版本變更
├── research_tree_overview.md  研究樹：假設 → 實驗設計 → 結果 → 推論 ⟹ 下一個假設
├── comparison_catalog.md      比較實驗總目錄：每組「A vs B」用統一格式列出，最後附變因索引
├── ideas/NNN-slug.md          想法演變：依時間遞增編號，每篇是一次思考轉折
├── papers/slug.md             文獻筆記：一篇論文一個檔案
└── experiments/exp-slug.md    實驗記錄：一組實驗一個檔案
```

空白模板在 `assets/templates/`。新專案用 `scripts/init_research_log.py` 建立骨架（見「工作流程 A」）。

## 核心原則與理由

### 1. 因果線分離（對付來源混淆）
研究通常會分岔成幾條**因果線**。典型的情況是：「原始研究動機」是一條，「看到實驗結果後才出現的貢獻定位或方法論問題」是另一條。每篇 idea 都要標明屬於哪一條，或開了一條新線。

理由：論文最容易出問題的地方，是把事後找到的優勢包裝成原始設計目標。這不誠實，審稿人也容易看穿。把線分開記錄，寫論文時才分得清「哪些是預先設計的、哪些是事後發現的」。各條線的定義寫在專案的 `research_log/README.md`。

### 2. 只追加、不改寫（對付後見之明偏誤）
舊的 idea 即使被推翻也保留，在 frontmatter 改 `status: refuted`，並在**文末**加「## 更新（日期）」段落說明新證據。不要回頭改寫原本的論證。

理由：被推翻的想法和推翻它的證據，本身就是研究軌跡的一部分。改寫後，就看不出當初為什麼這樣想，也就學不到教訓。允許的例外：修正錯字、錯誤的連結或編號，並在修改處註明。

### 3. 先寫預測，再看結果
設計實驗時，在 idea 或實驗記錄裡先寫下「預期會看到什麼、什麼結果會推翻假設」，結果出來後再對照。

理由：沒有事先寫下的預測，任何結果都能被事後解釋成「符合預期」。

### 4. 每個數字都要知道是怎麼量的
`methods.md` 登記每種評估協定：回答什麼問題、recipe、何時適用、已知陷阱。引用或比較數字前，先確認是同一個協定。協定有變更（例如資料產生方式、評估網格），在 methods.md 的「協定版本變更紀錄」寫下來。

理由：同一個模型用不同協定量，數字可能差很多，名稱卻一樣（例如都叫 accuracy 或 relL2）。混用是最常見的誤判來源。

### 5. 明確記錄「不可比之處」與資訊來源
文獻筆記要寫：問題設定、跟我們的可比性、**哪些地方不可比**、資訊來源（讀過全文、只讀摘要、二手摘要，還是憑記憶）。實驗記錄要寫限制（單一 seed、只測一種條件、硬體共用、結果無法重現等）。

理由：之後讀紀錄的人（包括未來的使用者和 Claude）會把它當成事實。如果沒標明來源強度，記憶或摘要就會被當成讀過全文的結論。

### 6. 可重現
每篇實驗記錄都要有：完整執行指令、程式版本（commit hash，如果有）、結果路徑、seed、硬體。

### 7. 假設狀態用固定詞彙
`open`（尚未驗證）、`planned`（已設計實驗）、`supported`（有證據但條件有限）、`confirmed`（多次或多條件驗證）、`refuted`（被推翻）、`superseded`（被更精確的假設取代）。結論只成立一半時，狀態欄要寫清楚哪部分成立、哪部分不成立。例如「結論成立，但原本提出的機制被推翻」。

## frontmatter 與連結

每篇 idea、experiment、paper 開頭放 frontmatter：

```markdown
---
type: idea | experiment | paper
status: open | planned | supported | confirmed | refuted | superseded | done
date: YYYY-MM-DD
related: [相對路徑, ...]
---
```

實驗另外加 `seeds:`、`results:`（結果路徑）；文獻另外加 `title`、`authors`、`venue`、`source`（資訊來源強度）。

檔案之間一律用**相對 markdown 連結**（例如 `[idea 003](../ideas/003-xxx.md)`），GitHub 和編輯器都點得開。寫完後執行 `scripts/check_links.py` 檢查連結是否斷掉。

## 工作流程

### A. 初始化新專案的 research log
1. 先問使用者，或從對話與計畫書整理出：專案名稱、目前的因果線（至少一條「原始研究動機」）、主要評估指標。
2. 執行：
   ```bash
   python <skill 目錄>/scripts/init_research_log.py <專案根目錄> --project "<專案名稱>"
   ```
   這會建立目錄和所有中樞檔案的骨架；已存在的檔案不會被覆蓋。
3. 填入 `README.md` 的因果線定義、`methods.md` 的第一個協定、`hypotheses.md` 的初始假設。如果有計畫書，寫成 `ideas/001-origin-<slug>.md`。
4. 如果專案已經有討論或實驗歷史，依時間順序補寫成 ideas 和 experiments，**明確標註是事後補記**。

### B. 記錄一組實驗結果（最常用）
依序更新以下檔案，漏掉任何一個，紀錄就會開始互相矛盾：
1. `experiments/exp-<slug>.md`：用 `assets/templates/experiment.md` 模板；動機、方法（完整指令）、結果表、結論（支持或推翻哪個假設）、限制。
2. `hypotheses.md`：更新對應假設的狀態和證據欄；如果出現新假設，加新列；更新最上方「當前最前沿的待分析問題」。
3. `comparison_catalog.md`：如果是「A vs B」比較，新增一條（比較內容、比較點、數據表格、簡單結論），並更新變因索引。
4. `research_tree_overview.md`：假設狀態改變時，更新對應的 block。
5. `methods.md`：如果用了新的量測方式或改變協定，登記或加版本紀錄。
6. 如果結果引發新的想法，另開 idea（工作流程 C）。
7. 執行 `scripts/check_links.py`；如果專案用 git，詢問或依使用者慣例 commit。

只寫有實際數據支持的東西。尚未執行的實驗標為 `planned`，不要寫得好像已經有結果。

### C. 記錄一次思考轉折（新 idea）
當討論中出現以下情況，就開新 idea：新的假設、對既有結果的新解讀、使用者提出的觀點、方向改變、決定放棄某條路。
- 編號接續 `ideas/` 中最大的號碼。
- 寫明：從哪個假設或實驗而來、屬於哪條因果線、論證、預測、接下來要驗證什麼。
- **使用者提出的想法要如實記錄**，包括哪些部分成立、哪些需要修正。不要只記修正後的版本，這樣才看得出思考怎麼演變。

### D. 整理文獻
用 `assets/templates/paper.md`。重點是「和我們的關係」和「不可比之處」。沒讀過全文時，在 `source:` 寫清楚，並列出「待辦：讀全文確認 X」。

### E. 回答「我們現在在哪」
讀 `hypotheses.md`（最上方的前沿問題）和 `research_tree_overview.md`，摘要：已確認的、被推翻的、正在進行的、等待決策的。回答時引用檔案連結。

### F. 根據紀錄撰寫論文、報告
- 依因果線分開敘述：原始動機寫在前言和方法；事後發現的寫成「進一步分析」或「討論」，**不要包裝成原始設計**。
- 引用的每個數字都要追溯到實驗記錄和協定。
- 被推翻的假設、已排除的論述，寫論文時也是有用的素材（例如消融、限制段落）。

## 寫作風格
- 用使用者和你對話的語言寫（例如繁體中文），技術名詞可保留英文。
- 每個 block 盡量精簡；表格優先於長段落。
- 數字要附單位、seed 數、協定名稱。
- 不確定的地方直接寫「推測」或「未驗證」，不要用模糊的語氣帶過。

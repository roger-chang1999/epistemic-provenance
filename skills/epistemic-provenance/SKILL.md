# Epistemic Provenance：知識來源追溯

> **為研究中的每個主張，保留它從哪裡來、憑什麼成立、怎麼被改變的完整紀錄。**

這個 skill 維護專案裡的 `research_log/`。目的是防範研究者騙到自己：把事後的解釋誤記成原始設計（來源混淆）、知道結果後改寫當初的推理（後見之明偏誤）、把不同方法量出的同名數字放在一起比（協定混用）。下面每條規則都對付其中一種；理解原因比死守格式重要，遇到格式沒涵蓋的情況，依原則判斷。

## 目錄結構

```
research_log/
├── README.md                  使用說明、本專案的因果線定義、給審查者的指引
├── hypotheses.md              中樞索引：所有假設與狀態；最上方是「當前最前沿的待分析問題」
├── methods.md                 評估協定登記表：定義、recipe、陷阱、版本變更
├── research_tree_overview.md  研究樹：假設 → 實驗設計 → 結果 → 推論 ⟹ 下一個假設
├── comparison_catalog.md      比較總目錄：每組「A vs B」用統一格式列出，附變因索引
├── ideas/NNN-slug.md          想法演變：依時間遞增編號，每篇是一次思考轉折
├── papers/slug.md             文獻筆記：一篇論文一個檔案
└── experiments/exp-slug.md    實驗記錄：一組實驗一個檔案
```

模板在 `assets/templates/`。平常只需要讀 `hypotheses.md`，其他檔案按需打開，不要整份紀錄從頭讀。

## 核心原則

1. **因果線分離**：研究會分岔成幾條因果線，例如「原始研究動機」和「看到結果後才出現的貢獻定位或方法論問題」。每篇 idea 標明屬於哪一條。理由：把事後找到的優勢包裝成原始設計，既不誠實，也容易被審稿人看穿。線的定義寫在專案的 `research_log/README.md`。
2. **只追加、不改寫**：被推翻的 idea 也保留，frontmatter 改 `status: refuted`，在文末加「## 更新（日期）」說明新證據。理由：改寫後就看不出當初為什麼這樣想。例外：修正錯字、錯誤連結或編號，並在修改處註明。
3. **先寫預測，再看結果**：實驗前寫下「成立時應看到什麼、什麼結果代表不成立」，並在關卡一**經使用者確認**。理由：沒有事先的預測，任何結果都能被解釋成符合預期；只由 Claude 寫，容易寫得太模糊。
4. **每個數字都要知道怎麼量的**：`methods.md` 登記每種評估協定；引用或比較前先確認是同一協定、同一版本；協定變更寫進版本紀錄。理由：同名的數字可能是不同方法量的，混用是最常見的誤判來源。
5. **不可比之處與資訊來源**：文獻筆記寫明可比性、**不可比之處**，以及 `source`（讀過全文／只讀摘要／二手摘要／憑記憶）。實驗記錄寫明限制。**文獻在被拿來比較、引用，或依其公式實作之前，必須讀完全文**，再把 `source` 更新為「已讀全文（日期）」；只讀過摘要的文獻只能用來發想。
6. **可重現**：實驗記錄要有完整指令、程式版本（commit hash）、結果路徑、seed、硬體。
7. **假設狀態詞彙**：`open`（尚未驗證）→ `proposed`（已提出設計，等使用者確認）→ `planned`（使用者已確認）→ `analyzing`（實驗已跑完，分析討論中，結論未確認）→ `supported`（有證據但條件有限）／`confirmed`／`refuted`（被推翻）／`superseded`（被更精確的假設取代）。結論只成立一半時，寫清楚哪部分成立。`confirmed` 的條件依主張類型而定，狀態欄要註明類型：

   | 主張類型 | confirmed 的條件 |
   |---|---|
   | 實作類（程式、公式實作正確） | 通過**有已知正確答案**的驗證測試（對照解析解、參考實作、等價性測試）；只確認跑得動的 smoke test 不夠 |
   | 實驗類（我們自己觀察到的現象） | 多個 seed 或多種條件下都成立 |
   | 依賴文獻的（機制解釋、引用他人結論） | 維持 `supported`，除非我們自己的實驗也獨立驗證 |
8. **記錄誰做的決定**：每個設計決策記下選項、選定、**決定者**（使用者／Claude 提議經使用者同意／Claude 預設未經討論／依文獻）、理由。理由：決策也有來源，「為什麼選這個值」在論文裡的分量取決於是誰、根據什麼決定的。

## frontmatter 與連結

```markdown
---
type: idea | experiment | paper
status: open | proposed | planned | analyzing | supported | confirmed | refuted | superseded | done
date: YYYY-MM-DD
related: [相對路徑, ...]
---
```

實驗另加 `seeds:`、`results:`；文獻另加 `title`、`authors`、`venue`、`source`。檔案之間用**相對 markdown 連結**。寫完後執行 `scripts/check_links.py`。

## Node 生命週期與人工關卡（核心工作流程）

研究以 **node**（一個假設，加上驗證它的一組實驗）為單位推進。每個 node 有兩個人工關卡，停下來和使用者討論、經確認後才往下走。理由：研究方向和實驗設計是使用者的研究判斷；Claude 先做完再說「你可以推翻」，推翻就要重跑，使用者也會傾向接受既成事實。

```
① 提出假設（idea；狀態 open）
② 關卡一：設計討論 → Claude 提出設計表 → 列出審查選項 → 使用者確認（proposed → planned）
③ 執行（長時間執行時不主動監控，等使用者說完成）
④ 關卡二：分析討論（狀態 analyzing；通常要來回很多輪，仍屬於同一個 node）
   ④-1 初步報告 → 停，等使用者回應
   ④-2 討論迴圈：一次釐清一兩個議題，必要時補做診斷 → 每輪記錄共識與未決事項
   ④-3 結論確認：Claude 整理結論 → 使用者明確同意
⑤ 記錄（工作流程 B）；結論確認之後，才提出下一個 node 的選項
```

**關卡一的設計表**至少包含：要回答的假設（H#）與因果線；變因、對照或基準、固定條件；評估協定與 seed 數；**預測**；成本估計；**需要使用者決定的地方**（列出選項和 Claude 的建議，不要自行選定）。確認後狀態改為 `planned`，決策寫進實驗記錄的「設計決策紀錄」。相關的一批實驗可以共用一次關卡一。只有影響**變因、指標或主張**的決策才需要經過關卡，作圖格式這類細節不必。

**關卡二是討論，不是一份報告。** 結論要經過多輪討論才會形成；下一個 node 是結論的產物，不是分析的附帶項目。理由：agent 傾向在一個回合內給出「完整」答案，把分析、結論、下一步一次包好，使用者面對的就變成既成的結論和選單，而不是一起推理。

- **④-1 初步報告**：結果 vs 預測、異常、實作和原文或設計的偏差、替代解釋（雜訊、混淆變因、實作錯誤、協定問題）、這個結果**不能**推論出什麼、審查選項。然後**停下**，問使用者的解讀，以及要先討論哪個議題。**這時不提下一個 node**，也不更新 hypotheses 的狀態。如果結果依賴的文獻還沒讀過全文，先讀完再報告。
- **④-2 討論迴圈**：每輪只處理一兩個議題。異常、實作錯誤、需要補的診斷實驗**留在同一個 node** 處理（補做的小實驗也要說明設計，經使用者同意才跑），不當成開新 node 的理由。每輪結束時，把使用者的解讀、達成的共識、仍未決的事項，如實寫進實驗記錄的「分析討論」，包括 Claude 認為需要修正的部分。審查選項在迴圈中隨時可以啟用。
- **④-3 結論確認**：Claude 認為議題都已釐清時，整理出「本 node 的結論、主張類型與狀態、限制、未決事項」，請使用者確認或修改。**使用者明確同意後**，才依工作流程 B 記錄，並更新 hypotheses 的狀態。
- **⑤ 下一個 node**：結論確認後，才提出 2–3 個選項，各自說明要回答什麼、成本、對主線的價值，附 Claude 的建議。使用者也可能在討論中自己提出方向，如實記錄。

**審查選項**：兩個關卡都**主動列出**下面兩項，使用者說要才做，可以都不做。可以附上 Claude 對「這次值不值得做」的看法（例如「結果違反預測，建議做嚴謹審查」），但決定權在使用者。有勾選式提問工具就用它（可複選），否則用條列文字詢問。
- **嚴謹審查**：找出謬誤、給出嚴謹的建議。做法與謬誤清單見 `references/rigor-review.md`。使用者若裝了 grill-me 這類追問型 skill，也可以改用。
- **文獻搜尋**：先提出具體的搜尋問題和理由，使用者同意後才搜尋。見 `references/literature-search.md`。

## 日常工作流程

**B. 記錄實驗結果**（關卡二結論確認之後；討論中只更新實驗記錄的「結果」和「分析討論」，狀態標 `analyzing`）。依序更新，漏掉任何一個，紀錄就會互相矛盾：
1. `experiments/exp-<slug>.md`（模板 `experiment.md`）：動機、預測、設計決策紀錄、方法、結果、分析討論、結論、限制
2. `hypotheses.md`：狀態與證據欄（註明主張類型）、新假設、最上方的前沿問題
3. `comparison_catalog.md`：A vs B 比較與變因索引
4. `research_tree_overview.md`：狀態有變的 block
5. `methods.md`：新協定或協定變更
6. 引發新想法時開新 idea；執行 `check_links.py`；依使用者慣例 commit

只寫有實際數據支持的東西；尚未執行的實驗標 `planned`。

**C. 新 idea**：出現新假設、新解讀、使用者的觀點、方向改變或放棄某條路時開一篇。編號接續最大號；寫明來源、因果線、論證、預測、下一步。**使用者的想法如實記錄**，包括哪些部分成立、哪些需要修正。

**D. 文獻筆記**：模板 `paper.md`；重點是「和我們的關係」「不可比之處」和誠實的 `source`。

**E. 回報進度與研究歷程回顧**：先判斷使用者要短版（「進度到哪」：只列前沿）還是完整版（「從頭回顧」「要跟老師報告」：**依研究的依賴順序逐 node 回顧**，不依主題重新分組），判斷不出來就問。做法見 `references/workflow-progress-report.md`。

**其他工作流程**（用到時才讀）：
| 情境 | 讀這份 |
|---|---|
| 初始化新專案的 research log | `references/workflow-init.md` |
| 回報進度、從頭回顧研究歷程、向老師或合作者報告進度 | `references/workflow-progress-report.md` |
| 審查紀錄本身有沒有錯（狀態不實、協定混用、結論超出證據）；交給他人看之前先做這個 | `references/workflow-review-log.md` |
| 根據紀錄撰寫論文、報告 | `references/workflow-writing.md` |

## 寫作風格
用使用者對話的語言寫，技術名詞可保留英文。表格優先於長段落。數字附單位、seed 數、協定。不確定就直接寫「推測」或「未驗證」。
